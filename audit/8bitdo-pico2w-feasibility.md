# 8BitDo 反编译源码适配 Pico 2 W 上位机：初步分析

分析日期：2026-10-11（香港时间）。

分析对象：`C:\Users\1\Desktop\prj\jiehsouqi\decompiled`，以及同级 `精英软件V2.16` 中的文件。对照固件：当前工作区 `pico2w` 的 R4.2。

## 结论

**技术上可以改造为我们的 Pico 2 W 上位机，但需要替换设备通信和配置后端；仅修改 VID/PID 不够。**

这份反编译结果主要提供 Windows 界面、配置数据结构和交互逻辑。设备枚举、配置读写、按键读取、部分校验与升级操作依赖厂商的原生 `8BitDoAdvance.dll`，这些实现没有出现在本次 C# 源码中。

最值得参考的是 USB 接收器分支 `UltmateAdvance` / `UltmateAdvanceUI`，它本来就是“接收器连接不同手柄”的模型。我们的 XSX、Switch Pro、Stadia 可以使用相似的界面组织，但需要自己的设备类型、能力描述和协议。

建议先做独立的 Pico 上位机：接通现有状态、电量和 XInput 测试，再扩展固件的映射、死区与配置保存。若目标是保留原软件的具体界面，可移植选定控件并接入同一套 Pico 后端。直接维护完整反编译工程，需要承担更多型号分支与旧实现的维护工作。

## 原软件的调用链及可复用部分

原配置流程大致为：界面编辑 → 全局配置模型 → AdvanceUI 转换 → AdvanceManage → 各型号 Advance → 厂商 DLL → 设备。

| 部分 | 源码入口 | 适配判断 |
|---|---|---|
| 设备发现 | `Advance.Hid/VIDPID.cs`、`SHid.cs` | 固定扫描厂商 VID `11720 = 0x2DC8` 及多个 PID；底层枚举交给 DLL。需替换为 Pico HID 枚举与协议验证 |
| 连接初始化 | `HIDManage.cs`、`DinputHid.cs` | 找到设备后还要读取厂商版本数据；新增 PID 仍无法通过现有初始化 |
| 接收器配置 | `Advance.Advances/UltmateAdvance.cs:115` | `readUSBAdapter` / `writeUSBAdapter` 都是原生调用；结构体可参考，实际通信需自己实现 |
| 配置调度 | `Advance.AdvancesManage/AdvanceManage.cs:46` | 有读、写、刷新、撤销的抽象入口，可参考；现有同步流程含固定等待，适配时应改为后台任务及明确回执 |
| 界面转换 | `Advance.AdvancesUI/UltmateAdvanceUI.cs:120` | 能看到摇杆范围、扳机范围、震动比例、映射和宏等如何填入配置结构；需替换厂商字段及型号判断 |
| 按键测试 | `Advance.View/TestView.cs:143`、`Advance.ConfidentialData/S_ReadKey.cs:10` | 原界面通过 DLL 的 `readKeys` 读取 64 字节厂商数据，不能直接解码我们的 XUSB；应接 XInput 或新增原始输入报告 |
| 配置文件 | `Advance.Tools/S_INI.cs`、`S_File.cs`、`Advance.View/ProFileView.cs` | 交互可参考；文件与 PID、平台和厂商结构关联，建议定义自己的版本化文件格式 |
| 校准 | `Advance.Hid/Calibration.cs` | 使用厂商校准命令；不能直接校准其他蓝牙手柄的原厂存储，可另做接收器侧软件校正 |
| 升级 | `Advance/S_ControllerUpdaterView.cs`、`Advance.Hid/S_Boot.cs` | 厂商升级流程需替换。当前 Pico 使用 BOOTSEL + UF2，保留此方式即可 |

这里的“复用”指技术上可移植或参考选定代码，并不表示整页复制后就能运行。多个页面通过单例、静态状态和 PID 判断直接访问设备型号。

原版本请求在 `DinputHid.cs:11` 中以 `81 05 00 21 01`（十六进制）开头，发送 64 字节并检查厂商返回数据。它与我们 `P2W` 状态协议无关。`Xinput.cs` 还通过震动序列执行厂商模式切换，不能将该流程当作普通的连接探测复用。

## 与当前 Pico 2 W 的接口差异

当前 USB 身份为 `2E8A:10C8`，设备版本 `0x0402`，接口 0 为 XUSB/XInput，接口 1 为系统 HID 状态接口。无线端一次连接一只 XSX、Switch Pro 或 Stadia。

源码依据：`pico2w/src/usb_descriptors.c:29`、`usb_xinput.c:108`、`bridge.c:29`、`platform.c:151`。

| 功能 | 使用现有固件能否实现上位机页面 | 进一步工作 |
|---|---|---|
| 接收器检测、手柄类型、已就绪/未连接 | 可以 | 读取现有 HID Feature，验证 Report ID、P2W 魔数与协议版本。当前没有扫描/配对阶段、地址等细分状态 |
| 电量 | 可以 | 复用现有电量工具的访问方法与解释规则；Switch 显示档位，BAS 显示百分比，Xbox HID 原始值保留原始单位 |
| 按键、双摇杆、LT/RT 测试 | 可以 | 通过 Windows XInput 读取；显示的是经过当前固定映射后的输出，不是全部原始蓝牙字段 |
| 双马达测试 | 固件已有通路 | 上位机可按选定 XInput 槽位发送测试指令；当前文档没有专项实物验收结论，需要后续确认 |
| 按键重映射、摇杆死区/反向、扳机范围 | 不可以直接设置 | 增加配置协议，并让固件在输入转换路径应用参数 |
| 震动强度比例 | 不可以直接设置 | 在接收器震动转发路径增加独立强/弱马达缩放，保留停止优先级 |
| 配置保存到接收器、多档配置 | 不可以 | 增加配置模型、Flash 存储、读回校验及版本迁移 |
| 宏 | 不可以 | 原源码有宏编辑数据；接收器还需按时间执行宏、处理触发/松开、断线取消与中立释放 |
| 电脑清配对、重启、进入刷机 | 不可以通过现有 HID 执行 | 目前清配对由 BOOTSEL 长按触发。若加软件操作，需要新增明确命令与结果状态 |
| Capture/Share/Assistant、陀螺仪显示 | 现有 XInput 不提供 | 先检查各解析器是否保留目标字段，再定义额外状态/输入报告；不能仅增加界面按钮 |

当前 `tud_hid_set_report_cb` 明确忽略所有写入。Report ID 1 为 32 字节状态报告（含 ID），其 payload 31 字节；不应将它解释为配置通道。

现有上位机基础已经在 `pico2w/tools/battery-monitor.ps1` 和 `test_windows.py`：前者使用 Windows SetupAPI / HID Feature API，后者调用 XInput。可直接参考我们的这些访问代码，无需逆向厂商 DLL。

同时插着其他 Xbox/XInput 手柄时，不能假定 Pico 总是 XInput 槽位 0。首版应让用户明确选定测试槽位；若要自动关联，应另行验证设备接口与 XInput 槽位的映射方案。现有电量报告没有槽位编号。

## 推荐实施顺序

1. **先完成基础上位机，固件暂不改动。** 显示 Pico 是否存在、手柄类型、电量、Xbox 标准按键、双摇杆和独立扳机；添加可选槽位的短时震动测试。利用现有 R4.1/R4.2 状态协议验证实际通信。
2. **定义我们自己的配置后端。** 可在现有 HID 接口新增独立 Report ID，包含协议版本、能力集合、命令、事务号、长度和结果码；不要用 C# 内存结构体直接充当 MCU 的线格式。保留旧 Report ID 1，保证电量工具兼容。
3. **先实现有限的可配置项目。** 按键映射、摇杆死区/反向、扳机范围、双马达比例；采用“编辑 → 校验 → 应用到 RAM → 读回 → 显式保存”的流程，写 Flash 不跟随每次滑块拖动。
4. **增加持久化配置。** 独立规划配置扇区、校验、默认值和损坏恢复。现有 `0x3FD000..0x3FEFFF` 属于配对 TLV，最后 4 KiB 为芯片勘误保留，不能直接占用；需同步调整应用空间边界和镜像校验。
5. **最后扩展宏和高级配置。** 支持范围由固件能力报告决定，避免出现页面可编辑但硬件没有实现的项目。宏应在接收器执行，应用关闭后仍可工作；断线、USB 休眠及配置切换必须取消宏并释放输入。

上述步骤 2–5 是设计建议，本次没有实现或验证。

## 两条改造路线

| 路线 | 优点 | 主要成本 | 判断 |
|---|---|---|---|
| 修复完整反编译工程，添加 PicoAdvance / PicoAdvanceUI，并替换 SHid 与测试读取 | 最大程度保留原界面和配置编辑体验 | 恢复编译依赖、替换原生调用、处理大量 PID 分支/静态状态/线程强制终止，移除厂商升级和模式切换链路 | 若明确要求保留原界面，可行，但不是只改几个识别值 |
| 建立独立 Pico 上位机，参考或移植选定交互/控件 | 与当前固件直接匹配，后端清晰，便于持续增加功能 | 需要搭建自己的界面与配置模型 | 建议作为当前起点 |

两条路线最终都需要同一套 Pico 配置协议和 MCU 功能。通过电脑界面编辑一个 INI 文件，不会自动改变当前接收器输出；要让游戏收到新映射，参数必须在接收器的输入转换流程生效。若选择完全在 PC 端拦截并重映射，则属于另一套输入转发架构，当前不需要引入。
